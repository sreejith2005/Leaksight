Build the database in strict layer order: RAW first, then Canonical, then Derived.
2.1 — RAW Layer Tables
Create SQLAlchemy models and Alembic migration for:
documents table — id (UUID), tenant_id, run_id (nullable at this stage), file_path, sha256_hash, doc_type (ENUM: INVOICE, CONTRACT, PO, GRN), file_size, page_count, created_at
raw_parses table — id, document_id (FK), raw_version (integer), parser_version (string), structured_output_jsonb, parse_confidence (float), created_at
Apply RLS policy to both tables on tenant_id
Write unit test: confirm raw_parses cannot be updated once inserted (application-level enforcement at this stage, DB trigger in Phase 5)
2.2 — Canonical Layer: Vendor Tables
Create SQLAlchemy models and Alembic migration for:
vendors table — id, tenant_id, normalized_name, raw_names_jsonb, gst_id (nullable), created_at
vendor_aliases table — id, tenant_id, vendor_id (FK), alias_name, override_source (ENUM: MANUAL_REVIEW, IMPORT, AUTO_ACCEPTED), applied_by_user_id, created_at, is_active (boolean)
Composite unique constraint on (tenant_id, alias_name) for vendor_aliases
RLS on both tables
Index on tenant_id, index on gst_id, index on alias_name
2.3 — Canonical Layer: Unit & Currency Tables
canonical_units table — id, name, symbol, dimension (ENUM: weight, volume, count, area, time)
unit_conversion_factors table — id, from_unit_id (FK), to_unit_id (FK), factor (numeric, high precision), tenant_id (nullable — NULL = system default), created_at
Composite UNIQUE on (from_unit_id, to_unit_id, tenant_id)
Seed migration: insert all V1 seed units (MT, KG, G, L, ML, Nos, Box, Set, Sqft, Sqm, RMT) and their conversion factors
fx_rates table — id, tenant_id (nullable), from_currency, to_currency, rate (numeric), rate_date, source (ENUM: ECB, RBI, MANUAL_UPLOAD, ADMIN_IMPORT), uploaded_by_user_id (nullable), created_at
Index on (from_currency, to_currency, rate_date)
2.4 — Canonical Layer: Contract Tables
contracts table — id, tenant_id, vendor_id (FK), created_at
contract_versions table — id, contract_id (FK), version_number, valid_from (date), valid_to (date), created_at
contract_line_items table — id, contract_version_id (FK), item_desc, unit, unit_price (numeric), currency
RLS on all three
Index on (vendor_id, valid_from, valid_to) for contract version resolution query
Write unit test for get_valid_contract_version(vendor_id, invoice_date) — covering: match found, overlap found (→ manual review flag), none found (→ skip Rule 1)
2.5 — Canonical Layer: Invoice, PO, GRN Tables
invoices table — id, tenant_id, vendor_id (FK), invoice_no, invoice_date, total_amount (numeric), currency
invoice_line_items table — id, invoice_id (FK), item_desc, quantity (numeric), unit, unit_price (numeric), line_total (numeric)
purchase_orders table — id, tenant_id, vendor_id (FK), po_no, po_date
po_line_items table — id, po_id (FK), item_desc, unit, ordered_qty (numeric), unit_price (numeric)
grns table — id, tenant_id, po_id (FK), grn_date
grn_line_items table — id, grn_id (FK), item_desc, unit, received_qty (numeric)
RLS on all six tables
Composite unique constraint on (tenant_id, invoice_no) for invoices
Add composite index on invoices: (tenant_id, vendor_id, invoice_date) — this is mandatory for Rule 2 near-duplicate scanning at 10,000+ invoices; without it the query degrades to a full table scan on filtered results
2.6 — Derived Layer Tables
analysis_runs table — id, tenant_id, status (ENUM: QUEUED, PROCESSING, PARTIAL_SUCCESS, COMPLETE, FAILED), error_summary (text, nullable), started_at, completed_at
leakage_records table — id, tenant_id, run_id (FK), leakage_type (ENUM: PRICE_MISMATCH, DUPLICATE_INVOICE, QUANTITY_MISMATCH), amount (numeric), currency, confidence (float 0–1), evidence_jsonb, rule_applied, status (ENUM: PENDING, ACCEPTED, REJECTED, PENDING_FX_RATE), review_notes (text, nullable), created_at
RLS on both tables
document_hashes table — id, document_id (FK), tenant_id, hash_sha256, hash_type (ENUM: BASELINE, REUPLOAD, PERIODIC_CHECK), upload_sequence (integer), comparison_status (ENUM: NEW, UNCHANGED, MODIFIED, INCONCLUSIVE), comparison_against_id (nullable FK to self), metadata_jsonb, risk_score (integer 0–100), flagged_anomalies_jsonb, created_at
2.7 — Tenant Settings Table
tenant_settings table — tenant_id (PK), abbreviation_dictionary (jsonb), fuzzy_threshold (float), duplicate_window_days (integer), manual_review_threshold (float), base_currency (char 3)
Seed defaults: fuzzy_threshold = 0.85, duplicate_window_days = 30, manual_review_threshold = 0.70, base_currency = INR
Seed abbreviation_dictionary with V1 defaults: document this structure explicitly — each entry is a key-value pair of raw abbreviation to normalized form (e.g. "MT" → "metric_ton", "NOS" → "nos"), stored as a flat JSON object, tenant can extend it but not delete system defaults

3.8 — Rules Engine
Create rules/rule_engine.py — orchestrator that takes a matched invoice line item and runs applicable rules
Create rules/rule1_price_mismatch.py 
Check contract validity on invoice date (use contract resolver)
Check unit compatibility (use unit converter)
Calculate overcharge amount: (invoice_unit_price - contract_unit_price_converted) × quantity
Populate evidence_jsonb with all required fields including unit_conversion_details and fx_rate_applied
Generate human-readable explanation string
Return LeakageRecord object or None
Create rules/rule2_duplicate_invoice.py 
Exact duplicate: same invoice_no + same vendor + same tenant
Near duplicate: same vendor + same amount + within duplicate_window_days — this query uses the composite index (tenant_id, vendor_id, invoice_date) created in Phase 2.5

Create rules/rule3_quantity_mismatch.py

PO fallback: if no GRN, compare invoice qty vs PO ordered_qty

4.8 — Parse Confidence Threshold Enforcement
After every parse result is returned by any parser, apply the following logic before writing to DB: 
If parse_confidence >= tenant.manual_review_threshold → proceed normally
If parse_confidence < tenant.manual_review_threshold → set a low_confidence flag on the document, still write the raw_parse row, still proceed to normalization, mark run status as PARTIAL_SUCCESS (do not halt processing)
This logic lives in services/parse_storage_service.py (see 4.9) as part of the storage step, not inside the individual parsers — parsers only return confidence, they do not make routing decisions
Write tests: high confidence document → proceeds clean, low confidence document → flagged + still processed + run becomes PARTIAL_SUCCESS

5.4 — Analysis Run Task
Create tasks/analysis_run_task.py
Task: run_analysis(run_id, tenant_id)
Sets tenant context
Loads all canonical invoices for the run
For each invoice line item: run vendor matching → run contract resolution → run rules engine → create leakage records
Run status logic (explicit, not implied): 
All documents parsed and all invoice line items processed cleanly → status = COMPLETE
One or more documents had parse_confidence < manual_review_threshold → status = PARTIAL_SUCCESS
One or more invoice line items resulted in PENDING_FX_RATE → status = PARTIAL_SUCCESS
Both of the above present → status = PARTIAL_SUCCESS
Unhandled exception on the run itself → status = FAILED, write error_summary
PARTIAL_SUCCESS and FAILED can coexist per document but the run-level status reflects the worst non-fatal state
On any unhandled exception at run level: set status FAILED, write error_summary, do not silently drop

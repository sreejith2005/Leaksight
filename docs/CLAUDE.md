# CLAUDE.md — LeakSight V1 Coding Conventions & AI Rules

## Purpose

This file defines the non-negotiable rules, coding conventions, and locked architectural decisions for the LeakSight V1 project. Any AI assistant (including GitHub Copilot, Claude, or similar tools) working on this codebase **must** follow these rules without exception.

---

## Non-Negotiable Rules

These are absolute constraints. They cannot be overridden, relaxed, or worked around.

### 1. No Vector Embeddings

- Do **NOT** use vector embeddings, semantic search, or any ML-based similarity matching for item matching, vendor matching, or any matching task.
- Use **RapidFuzz** (token_sort_ratio) for all fuzzy matching.
- Reason: Determinism. Two identical inputs must always produce identical outputs. Embeddings introduce model-version drift and non-reproducible results.

### 2. No Outbound Internet from Workers

- The Celery worker container must have **no outbound internet access**.
- Workers operate on an internal-only Docker network.
- No fetching FX rates from APIs, no downloading models at runtime, no phoning home.
- All data (FX rates, OCR models, dictionaries) must be pre-loaded or manually uploaded.

### 3. No Real-Time Processing

- LeakSight is a **batch processing system** used quarterly.
- No WebSocket connections, no streaming, no live dashboards, no SSE.
- Users upload documents, trigger a run, and check results later.
- Polling for run status is acceptable. Real-time push is not.

### 4. No Silent Failures

- Every failure must be logged, flagged, and surfaced to the user.
- If a parser cannot extract a required field, it must add a `FailureFlag` — never skip silently.
- If a rule cannot execute (e.g., no contract found), it must log the reason and set `confidence = 0`.
- If an analysis run fails partially, the run status must be `PARTIAL_SUCCESS`, not `COMPLETE`.
- No empty catch blocks. No swallowed exceptions.

### 5. No Price Guessing

- If a contract line item cannot be matched to an invoice line item, do **NOT** guess the price.
- Set `confidence = 0` and skip. The human reviewer decides.
- The fuzzy matching threshold is configurable per tenant (`fuzzy_threshold`), default 0.85.
- Below threshold = no match = no leakage calculation.

### 6. No FX Rate Guessing

- If a currency conversion is needed and no FX rate exists for the required date + currency pair:
  - Set leakage record status to `PENDING_FX_RATE`.
  - Do NOT use a "closest date" rate, do NOT use a default rate, do NOT hardcode a rate.
  - The admin must upload the correct rate manually.

### 7. No Implementation Before Specification

- Never write implementation code before the relevant spec document in `/docs` is complete.
- If asked to implement a feature whose spec doesn't exist, create the spec first.

### 8. No Kubernetes, No Microservices

- This is a **monolithic backend** deployed on a single Hetzner CX41 server via Docker Compose.
- No Kubernetes, no service mesh, no container orchestration beyond Docker Compose.
- No splitting the backend into separate services. Internal modularity via Python packages only.

## Coding Conventions

### Python

- **Python 3.11+** (target runtime)
- **Type hints on all function signatures** — no `Any` unless absolutely unavoidable
- **Pydantic v2** for all request/response schemas
- **async def** for all FastAPI route handlers
- **sync def** for all Celery task functions
- Imports: stdlib → third-party → local, separated by blank lines
- Line length: 100 characters max
- Docstrings: Google-style
- Naming: `snake_case` for functions/variables, `PascalCase` for classes, `UPPER_SNAKE_CASE` for constants
- No `print()` statements — use `structlog` for all logging
- No `*` imports — always import explicitly

### Database

- All money amounts: `NUMERIC(20,6)` — never `FLOAT` or `REAL`
- All confidence scores: `FLOAT` in range `[0.0, 1.0]`
- All primary keys: `UUID` generated by `uuid_generate_v4()`
- All timestamps: `TIMESTAMPTZ` with `DEFAULT NOW()`
- Table names: `snake_case`, plural (e.g., `invoices`, `leakage_records`)
- Column names: `snake_case`
- Foreign keys: always named `{referenced_table_singular}_id`
- Indexes: named `idx_{table}_{columns}`
- RLS policies on every tenant-scoped table — no exceptions

### API

- All endpoints under `/api/v1/`
- RESTful conventions: `GET` for reads, `POST` for creates/actions, `PUT` for updates
- All responses: JSON with consistent error format
- All list endpoints: paginated (page/page_size/sort_by/sort_order)
- HTTP status codes: `200` (OK), `201` (Created), `202` (Accepted/Queued), `400` (Bad Request), `401` (Unauthorized), `403` (Forbidden), `404` (Not Found), `409` (Conflict), `422` (Unprocessable), `500` (Internal Error)

### Docker

- Single Dockerfile with multi-stage build
- Two entry points: `CMD` switches between `uvicorn` (API) and `celery` (worker)
- No `latest` tags — always pin image versions
- `.env` file for configuration — never hardcode secrets
- Health checks on all containers

### Testing

- `pytest` for all tests
- Test files: `test_{module}.py`
- Test functions: `test_{scenario}_{expected_result}`
- Fixtures for database setup/teardown
- No tests that require internet access
- No tests that depend on external services (mock everything)

### Git

- Branch naming: `phase-{N}/{short-description}` (e.g., `phase-1/docker-compose`)
- Commit messages: `[Phase N] Short description` (e.g., `[Phase 0] Add API contracts spec`)
- No force pushes to main
- Each phase = one PR with passing tests before merge

## Locked Architectural Decisions

These decisions are final. Do not revisit or propose alternatives.

| Decision | Chosen | Rejected Alternatives | Reason |
|---|---|---|---|
| Matching algorithm | RapidFuzz | Vector embeddings, Levenshtein | Deterministic, explainable, no GPU, C++ core |
| OCR engine | PaddleOCR 2.9 | Tesseract, Google Vision | Superior table/layout detection, runs offline |
| PDF rendering | WeasyPrint | ReportLab, wkhtmltopdf | HTML-to-PDF with CSS control, no binary deps |
| Database | PostgreSQL 15 | MySQL, MongoDB | RLS, JSONB, pg_trgm, extensions ecosystem |
| Task queue | Celery + Redis | RQ, Dramatiq | Mature, well-documented, easy monitoring |
| Backend framework | FastAPI | Django, Flask | Async, Pydantic validation, auto-docs |
| Frontend | React + TypeScript | Vue, Angular | Hiring pool, ecosystem, TanStack compatibility |
| Deployment | Docker Compose / Hetzner | Kubernetes, AWS | Cost (₹1,600/month), simplicity, single server |
| Tenant isolation | PostgreSQL RLS | Schema-per-tenant, app-level filtering | Defence in depth, database-enforced |
| Fuzzy matching library | RapidFuzz | fuzzywuzzy, thefuzz | C++ core, maintained, drop-in compatible |

## Logging Convention

- Use `structlog` with JSON output
- Always include: `tenant_id`, `user_id` (if available), `action`, `result`
- Never log: passwords, tokens, PII, file contents
- Log levels:
  - `ERROR`: Something failed that needs attention
  - `WARNING`: Something unexpected but handled (e.g., low confidence parse)
  - `INFO`: Normal operations (e.g., "run started", "file uploaded")
  - `DEBUG`: Detailed diagnostic info (e.g., matching scores, parser output)

## Performance Constraints

- **Max file size:** 200MB per upload
- **Max concurrent Celery workers:** 2 (Hetzner CX41 = 4 vCPU)
- **Worker memory limit:** 4GB per worker
- **PaddleOCR:** Mobile model only, page-by-page processing, `gc.collect()` after each page
- **API response time target:** <500ms for reads, <2s for writes (excluding file upload)
- **Database connection pool:** max 20 connections
- **Redis memory limit:** 512MB
